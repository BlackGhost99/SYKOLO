# YEM Parents — lot Android 1 : entrée famille dédiée

L'entrée HTTPS `/?app=parents#/parents` réutilise la version web et le logo YEM. Elle masque les choix établissement, plateforme et démonstration. Une session de gestion déjà ouverte n'affiche aucun tableau de bord de gestion ; le parent peut la fermer puis se connecter en tant que parent. Les contrôles d'autorisation restent sur le serveur Django : ce paramètre d'interface ne constitue pas une frontière de sécurité. Le site général est inchangé.

Ce lot prépare le futur APK mais ne contient ni binaire APK, ni signature Android, ni notifications push natives. Le choix du conteneur Android doit être validé avec les fonctions de téléchargement PDF, téléversement de pièces, liens de récupération de compte, notifications et navigation externe. Ne pas activer les paiements réels en contournant les gates du serveur. Tester sur Android physique avant publication. Le développement reste sur une branche indépendante jusqu'à sa recette. Aucun changement de base de données.

## Lot 2 — conteneur Android

L’APK de test utilise uniquement `https://yem-api.onrender.com/parents-app/`. Une ancienne version du serveur ne possède pas cette route et affiche une erreur, pas l’interface générale. Projet Java/Android natif, rendu WebView des écrans YEM, Android 8+ (API 26), SDK 35, AGP 8.13.2 et Gradle 8.13. HTTPS obligatoire, filtre strict de l’origine et du chemin principal, aucun pont JavaScript natif, cookies tiers interdits, erreurs SSL jamais ignorées, sauvegarde Android désactivée, protection des captures d’écran. Aucun secret marchand dans l’APK. Les autres liens sont actuellement refusés. Les PDF, pièces jointes, liens externes et notifications natives restent à intégrer dans un lot séparé. L’APK debug GitHub Actions est uniquement destiné aux essais, non signé pour commercialisation ; la clé de production doit rester hors dépôt. Compilation locale : JDK 17, Gradle 8.13, SDK Android 35, puis `cd android && gradle :app:assembleDebug`. Le workflow génère le fichier APK en artefact si la compilation réussit. Installer seulement après déploiement de la route et vérifier sur appareil réel.

## Lot 3 — documents Android

Sélecteur Android SAF (PDF/JPEG/PNG) sans permission générale de stockage, puis contrôle serveur existant. Téléchargements authentifiés uniquement sur les routes PDF parents autorisées, sans redirection, taille maximale 15 Mio, contrôle MIME et signature %PDF-, copie temporaire privée puis choix explicite du fichier de destination. Les liens Ouvrir et Télécharger proposent actuellement tous deux l’enregistrement, pas de lecteur PDF intégré. Les fichiers enregistrés hors de YEM ne sont plus sous son contrôle. Validation sur appareil indispensable, notamment téléversement depuis un fournisseur de contenu et refus des liens externes. Le workflow utilise sdkmanager fourni par le runner plutôt que le paquet obsolète tools.

## Lot 4 — alertes natives, première étape

Opt-in explicite, permission Android 13+, canal géré par Android, lecture authentifiée de /auth/me puis /parents/notifications toutes les 60 secondes uniquement au premier plan. Première lecture silencieuse, comparaison en mémoire des identifiants/états, une alerte générique pour les nouveautés ; pas de texte d'école, d'enfant ou de montant sur écran verrouillé. Annulation et effacement de l'état local à la mise en arrière-plan, au changement de compte ou en cas d'échec de lecture. Aucune donnée scolaire persistée par ce composant. Ce n'est PAS du push lorsque l'application est fermée. Pour cette fonction : projet Firebase Cloud Messaging (FCM), association authentifiée et révocable appareil/compte, secrets serveur hors GitHub, envoi après commit avec reprises, contenu générique et tests sur Android physique. Ne pas inventer des identifiants Firebase ni ouvrir un nouveau service sans configuration.

Le second essai de CI a montré que sdkmanager n'est pas dans le PATH du runner ; utiliser setup-android@v4 avec les seuls packages SDK requis (la version 4 exclut le paquet tools obsolète).

## Lot 4b — registre serveur FCM

Le point d’entrée POST/DELETE `/api/v1/parents/push-device` est désactivé par défaut. Inscription d'un jeton par session Django parent, chiffrement Fernet avec clé dédiée d'au moins 32 caractères, empreinte unique, aucune restitution du jeton. La déconnexion supprime la session et son association. Une nouvelle session peut réassocier le même jeton ; aucun compte fourni par le client. Le registre conserve une date de départ et impose une limite de dix installations actives par parent. `YEM_PARENT_PUSH_ENABLED=true` et `YEM_PARENT_PUSH_KEY` restent à configurer côté serveur uniquement après validation. Le lot n'envoie pas encore de messages FCM : connexion Android au SDK, expéditeur et planification fiables sont à réaliser puis tester. Ne jamais inclure une clé de compte de service dans le dépôt ou l'APK.

## Lot 4c — réception Android FCM

Dépendances Firebase BoM 35.2.0 et Google services 4.6.0. Le fichier Android `android/app/google-services.json` est ignoré par Git, et le plugin ne s'applique que si le fichier existe. L'initialisation automatique FCM est désactivée par défaut ; aucun jeton demandé sans opt-in et session parent vérifiée. Le client enregistre le jeton par POST avec cookie Django et CSRF, et le révoque au mieux par DELETE à la désactivation. Les messages data-only `kind=family_update` sont transformés en notifications locales génériques si le consentement et l'association locale de courte durée restent valides. Aucun nom ni montant n'est transmis. Après huit heures au maximum, la session et l'association nécessitent une nouvelle connexion. Le service FCM expéditeur et la configuration Firebase réelle restent à faire. Les builds CI sans configuration Firebase valident la compilation uniquement, pas la réception réelle. Le bouton d'alerte reste facultatif, et la boîte YEM reste la source officielle.

## Lot 4d — expédition FCM (boîte durable)

La commande `python backend/manage.py yem_send_parent_push --limit 50` découvre les messages persistés non lus de la boîte école→parent, postérieurs à l'inscription de l'appareil, puis crée au plus une livraison par appareil et message. Vérification de session Django, identité, hash d'authentification, établissement actif et destinataire juste avant l'envoi. FCM HTTP v1, OAuth service account signé RS256, URL fixes, redirections refusées, TTL cinq minutes, contenu générique data-only. Reprises bornées avec temporisation exponentielle et Retry-After ; suppression de l'appareil en cas de UNREGISTERED explicite. Une acceptation FCM n'est pas une preuve de lecture ni de livraison ; après un crash entre acceptation et mise à jour DB, un doublon reste possible (collapse key et notification Android remplacée). Les événements calculés à la volée (échéances), les AdmissionsEvent et autres événements hors boîte durable nécessitent encore leur raccordement. Le worker doit être planifié par l'exploitant (par exemple toutes les minutes sur hôte privé) ; aucun cron actif ni identifiant externe créé. Secrets `YEM_FCM_SERVICE_ACCOUNT_JSON`, `YEM_FCM_PROJECT_ID`, `YEM_PARENT_PUSH_KEY` hors dépôt. Ne pas activer le service avant configuration, tests et recette.

## Lot 4e — événements pédagogiques

La publication d’un bulletin, d’une évaluation renseignée ou la clôture d’un appel avec absence/retard crée dans la même transaction un message durable par enfant et parent autorisé. Aucun brouillon, présence ordinaire ou enregistrement intermédiaire. Le filtre `guardian_links` contrôle le rôle et le rattachement à la création, à la lecture et avant expédition. Clé d’événement unique pour les répétitions. Les notices anciennes non liées à un enfant restent compatibles. Les événements financiers/admission calculés à la volée restent à raccorder sans doubler la boîte existante. Migration 0065 additive, pas de réécriture des dossiers.

## Lot 4f — admissions et finances

La commande de livraison projette les décisions d'admission et états terminaux PayCentral ainsi que SingPay et les échéances/retards déjà calculés dans la boîte push interne. Pas de duplication de la boîte web : les lignes `push-source:` sont masquées et non modifiables via l'API de lecture. Réévaluation de la dette, des droits et de l'état du paiement avant chaque envoi ; aucune modification du grand livre ni des admissions. Une alerte de retard est produite au passage échéance→retard, pas chaque jour. Pas de rattrapage des événements antérieurs à l'inscription de l'appareil ; les historiques demeurent visibles dans le portail. L'envoi ne concerne que les appareils et sessions valides, et reste désactivé par défaut. Tests du lot à valider. Les confirmations réelles SingPay et FCM nécessitent encore la recette prestataire.

## Mise en service — contrôles bloquants

Le workflow manuel `android-release.yml` est réservé à main et à l'environnement GitHub `android-release`. Configurer des approbateurs et limiter cet environnement à main. Créer le projet Firebase YEM et l'application `com.bwetek.yem.parents`, télécharger sa configuration Android, puis renseigner les secrets d'environnement `YEM_FIREBASE_ANDROID_JSON_B64`, `YEM_ANDROID_KEYSTORE_B64`, `YEM_ANDROID_KEYSTORE_PASSWORD`, `YEM_ANDROID_KEY_ALIAS`, `YEM_ANDROID_KEY_PASSWORD`, et la variable `YEM_ANDROID_SIGNER_SHA256` (empreinte SHA-256 du certificat de signature attendu). Conserver la clé de signature originale en lieu sûr hors GitHub ; ne pas partager les mots de passe dans une conversation. Aucun APK debug ne doit être présenté comme release. Le workflow refuse une signature différente et construit uniquement sur main, sans publier sur Play Store.

Serveur : définir sur le worker privé les trois paramètres Firebase et le chiffrement décrits plus haut, partager la clé de chiffrement avec Django, conserver YEM_PARENT_PUSH_ENABLED=false jusqu'à recette, configurer un cron dédié avec `python backend/manage.py yem_send_parent_push --limit 50` (pas de cron créé). Les sessions actuelles expirent après huit heures : le push ne couvre pas une période illimitée sans reconnexion. Une association durable révocable serait requise pour notifications multi-jours. Tester les sessions expirées, la déconnexion, les droits d'accès, les PDF, les justificatifs, l'absence de doublons, le réseau, et confirmer réception réelle après fermeture de l'APK. Aucun lancement public avant réussite des tests, signature, recette physique et vérification des prérequis de production. La sauvegarde de production reste une opération distincte reportée ; le test synthétique ne la remplace pas.

## Stabilisation — autorisation durable de notifications

Bail de notification distinct de la session web : 30 jours, renouvelable après authentification. Aucune prolongation de session web (8 h), aucune lecture ni action scolaire permise par ce bail. La déconnexion explicite et le changement de compte associés à une session révoquent l'appareil ; suppression d'une session expirée conserve le bail, changement de mot de passe et désactivation du compte invalident l'envoi. Le choix local de désactiver les alertes supprime immédiatement l'affichage, même hors connexion, et tente de retirer le jeton FCM. Un message générique déjà en transit peut arriver après révocation. À valider sur appareil et CI ; aucune activation réelle. Migration 0066, anciennes associations sans bail inactives. Prévoir également une gestion à distance des appareils avant diffusion large.

## Configuration Firebase existante

Le projet Firebase enregistré est `sykolo`, pour le package `com.bwetek.yem.parents`, validé sur le fichier de configuration Android fourni le 16 novembre 2026. Le fichier JSON n'est pas ajouté au dépôt public. Dans l'environnement GitHub protégé `android-release`, renseigner le secret `YEM_FIREBASE_ANDROID_JSON_B64` à partir du fichier original encodé en base64 ; la chaîne release vérifie le project_id et le package avant compilation. Le worker FCM utilisera `YEM_FCM_PROJECT_ID=sykolo` et les identifiants d'un compte de service doté du rôle Firebase Cloud Messaging API Admin, jamais le fichier client Android comme clé serveur. Activer l'API FCM HTTP v1. Les identifiants serveur et la clé de signature sont à saisir dans les espaces secrets autorisés ; ne jamais les commettre.

Correctif CI : les trois erreurs de lecture des notifications sur PostgreSQL sont dues à SELECT FOR UPDATE appliqué à une jointure nullable. Limiter le verrou à la notification elle-même (`of=("self",)`), en conservant les filtres d'autorisation des parents et le verrou transactionnel. Relancer la suite complète.
